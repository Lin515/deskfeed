# HTTP 取数规则与实现

桌面端只发 GET，只接纳 **HTTP 200 + UTF-8 JSON** 的正文。

## 规则

- 接受本地或远程 HTTP/HTTPS 地址；`http` 与 `https` 之外一律拒绝。
- 最终响应必须是 200。204、304、3xx（没有可跟的 Location）、4xx、5xx 都**不是**快照；
  清空必须以 `200` 返回合法的 `items: []` 表达。
- 允许开头的 UTF-8 BOM。
- 生产端建议声明 `Content-Type: application/json`；桌面端以正文校验为准，不仅凭响应头判定。
- 有界重定向：最多 **5** 跳，由主进程自己跟（不交给 WinHTTP 的自动策略）；**禁止 HTTPS 降级到
  HTTP**；重定向不改写保存的配置地址。
- 手动刷新只是立即重新 GET 原 URL，不追加 `refresh=1` 或任何专有参数。
- 不使用系统代理（`NO_PROXY`）：回环与局域网端点直连，也避免离线时自动代理探测白等。
- 第一版不加入厂商鉴权或自定义请求头；上游采集凭据由生产端掌握。

## 调度

| 配置 | 默认值 | 允许范围（实现选择） |
| --- | ---: | --- |
| 正常轮询周期 `poll_ms` | 30000 ms | 1000 .. 86400000 ms |
| 失败重试周期 `retry_ms` | 5000 ms | 1000 .. 3600000 ms |
| 请求超时 `timeout_ms` | 8000 ms | 1000 .. 60000 ms |

- 支持秒级轮询（下限 1000 ms）。
- 值是 0 或缺失表示“用默认值”；越界值夹到边界并把原因写进下一次启动的日志。
- 刷新、失败重试、请求超时都由桌面端配置；**不接受快照里的调度指令**。
  这些上下限属于实现细节，不是用户已确认的协议常量。

## 墙钟预算与线程模型

- 取数跑在独立工作线程上，主进程的消息循环只处理命令、到期与状态提交，始终响应。
- `timeout_ms` 是**整次取数的墙钟预算**：包含名字解析、连接、发送、响应头、重定向与正文读取。
- 共享 HTTP 层用**异步 WinHTTP**实现真正的整次取消，而不是“每次阻塞调用前重设 WinHTTP 超时”。
  后者约束不了已在途的响应头等待与逐块滴流的正文：四段超时各自独立，且超时只在请求发出前
  可靠生效，慢头部 + 慢滴流可以让一次取数花掉好几个预算（实测预算 800/1200/3000 ms 都停在
  约 4 s 的固定天花板）。现在的模型是：
  1. **驱动线程**（发起取数的那一条）独占全部句柄操作：发起一步、等这一步的完成通知，再发起
     下一步；完成回调只记状态并唤醒等待者，不碰任何 WinHTTP 调用。整次预算就是等待里的截止。
  2. 到点或被要求取消时，**关闭在途的请求句柄**。异步操作尚未完成时关闭相关句柄是文档化的
     取消方式；驱动线程此刻没有卡在 WinHTTP 调用里，所以不存在跨线程关句柄的竞态。
  3. 取消标志（换源、收尾）大约每 50 ms 检查一次，换源能立刻停掉旧源的请求。
  4. 每个句柄各自持有一份上下文强引用，只在自己的 `HANDLE_CLOSING` 里归还；正文读的落地
     缓冲区也由上下文持有，取消时在途的那次读仍有合法内存可写。异步操作的 OUT 参数一律传
     `NULL`（官方安全须知），字节数只从完成通知里取。
- `deskfeed.exe` 自己还会守一次截止：到点立刻更新状态机、按作业号丢弃结果。这一层是状态机
  层面的兜底；底层现在真的会在预算附近收手，被放弃的作业不再占着名额。
- 收尾不会等待数分钟：先置取消标志，等待有上限，超出就让进程退出收掉线程。

## 错误分类

`kind`（检查器输出与 `--inspect` 的 `view.failure`）：

| 名称 | 含义 |
| --- | --- |
| `invalid-url` | 地址不合法或协议不是 http/https（`--inspect` 里归到 `transport`）。 |
| `connect` | 名字解析不了、连不上、连接中断、TLS 握手失败。 |
| `timeout` | 超过整次取数的墙钟预算。 |
| `send` / `receive` | 请求发不出去 / 收响应出错。 |
| `redirect` | 重定向超过 5 跳，或试图从 HTTPS 降级到 HTTP，或 Location 解析失败。 |
| `http-status` | 上游返回非 200（含 204 / 304）。 |
| `too-large` | 正文超过 1 MiB。 |
| `empty` | 正文为空。 |
| `aborted` | 主进程要求取消（换源或收尾），不算失败。 |

正文读进来之后，`encoding` / `parse` / `validation` / `too-large` 等分类由协议校验给出，见
[protocol.md](protocol.md)。

## 与检查器的关系

`deskfeed-check --url <地址>` 调用的是**同一份** `http_get` 与 `snapshot_validate`，
所以“主进程会接纳什么”可以用一条命令离线问清楚。检查器不建互斥体、不开窗口、不注入任何进程。
