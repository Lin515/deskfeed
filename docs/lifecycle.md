# 命令、单实例与生命周期

## 命令行

冻结的四种形式：

```text
deskfeed.exe --url "<URL>" --pid <PID>   设置/切换地址，并绑定指定生产者进程（默认允许接管现有实例）
deskfeed.exe --url "<URL>"               设置/切换地址，同时解除原来的 PID 绑定，转为独立生命周期
deskfeed.exe --quit-if-bound <PID>       仅当前绑定 PID 匹配时正常退出
deskfeed.exe                             无参数：已有实例不接管；否则用最后保存的地址独立启动
```

行为：

- `--pid` 必须与 `--url` 同时使用；单独的 `--pid` 拒绝。`--pid` 等于调用方自己的 PID、`0`
  或 `4`（System）都拒绝。
- 单实例范围是**同一 Windows 用户、同一登录会话**，由命名互斥体仲裁；第二个进程只转发命令或
  失败退出，不做取数、不注入、不启动任何常驻工作。
- 已有实例时通过 IPC 转发**原始命令参数**；接收端重新校验并提交，不在窗口消息处理器里等待网络。
- 默认允许抢占，以最后一份有效接管请求为准，不弹确认。
- URL 按完整输入字符串比较：不猜测大小写、转义或尾斜杠是否等价。**带 PID 的命令即使 URL 相同也
  必须实际执行重绑**。
- URL 在命令被成功接纳时总是持久化；PID、进程句柄、绑定代次**永不持久化**。
- PID 不存在、已退出、无法访问或不合法时，拒绝**整条命令**；保持原磁盘 URL、运行时 URL、绑定与
  缓存不变。首次启动同样报错并退出。
- URL 保存失败也拒绝整条接管，原配置、绑定、缓存均不变。
- 绑定用进程句柄等待退出（`SYNCHRONIZE`），不轮询 PID，也不自动绑定短命的转发进程。
- 新绑定生效后，旧生产者退出不得关闭当前实例；旧 HTTP 请求迟到也不得覆盖新源。

### 附加开关（实施层，不改变上面四种形式）

| 开关 | 作用 |
| --- | --- |
| `--quit` | 无条件正常退出运行中的实例。 |
| `--wait-exit-ms <1..60000>` | 只与 `--quit` / `--quit-if-bound` 同用：确认被接受后**等到实例进程真的退出**才返回 0。缺省 0 = 旧语义（只等 IPC 确认）。见下面“条件退出与等到实例真的退出”。 |
| `--inspect` / `--dump-state` | 查询运行中的实例并打印一行 JSON；不会新建实例。 |
| `--poll-ms` / `--retry-ms` / `--timeout-ms <毫秒>` | 随 `--url` 一起提交调度配置；越界值夹到边界。 |
| `--scope <名字>` / `--test-instance <名字>` | 隔离命名空间（互斥体、控制窗口类名、设置文件、日志）。名字限 `[A-Za-z0-9_-]`、长度 1..32，其它一律用法错误；显式空串也拒绝。环境变量 `DESKFEED_SCOPE` / `DESKFEED_TEST_INSTANCE` 提供同样的作用（开关优先）。 |
| `--state-dir <目录>` | 本次运行改用该目录下的 `settings.ini`。 |
| `--headless` | 本次运行既不显示悬浮窗，也不做任何任务栏/注入工作（不落盘）。 |
| `--no-inject` / `--no-taskbar` | 本次运行不碰任务栏（不落盘）。 |
| `--hidden` | 本次运行悬浮窗保持隐藏（不落盘）。 |
| `--mock` | 只是 `--headless` 的别名；**不伪造、不改变任何数据行为**。 |
| `--frame-mailbox` | 按 `--scope` 建一块隔离的显示邮箱，**只给离线验收用**：必须与 `--scope` 以及 `--headless` / `--no-inject` 同时出现；它只建命名对象，不碰界面。建不起来就是启动失败（不静默继续）。 |
| `-h` / `--help` / `/?` | 打印用法。 |

隔离实例永远不会打开生产命名空间的对象，所以既不会抢生产实例的单例，也不会被它挡住。

## 启动顺序（不得颠倒）

1. 仲裁单实例（命名互斥体）。
2. 建立并接好控制窗口（接收端就绪）。
3. 才截断日志、写运行状态、启动取数线程。

在接收端就绪之前不做第 3 步，是为了让第二个实例的转发命令不会撞上一个还没准备好接收的实例。

## 控制通道

- 命名互斥体仲裁单实例；一个稳定的隐藏窗口接受 `WM_COPYDATA`；发送端用有界的
  `SendMessageTimeoutW`。
- 载荷是“协议版本 + 操作码 + 发送方 PID + 参数表”的二进制形式，**不包含发送进程的私有地址**；
  接收端在窗口消息处理器里把参数复制出来，绝不保存 `lpData` 指针。
- 载荷长度、参数个数、参数长度都有上限（64 KiB / 64 项 / 每项 4 KiB），越界即拒绝。
- 命令与接收端都只按**同一 Windows 用户**工作：命名对象带当前用户 SID 的短哈希并只授权给当前
  用户；接收端还会核对发送方进程的属主与自身一致。
- 第一版按同完整性级别使用。低完整性发送端不能假定能控制提升权限的接收端；不做权限绕过。

## 配置事务与失败顺序

一次接管按固定顺序提交：

1. 校验 URL（只接受 http/https，且主机名非空）。
2. 打开生产者进程句柄并**准备**等待者（此阶段失败不碰旧绑定）。
3. 把 URL 与随命令给出的调度值写进设置文件（同目录临时文件 + 刷盘 + 原子替换）。
   失败则放弃准备阶段，旧绑定与旧运行时状态不变。
4. 提交运行时：换源时递增数据源代次、清空旧源缓存、丢弃旧源在途响应并立刻取新源；
   然后提交绑定（或解除绑定）。

设置文件写入只改自己负责的那一行，其它栏目、键、注释与顺序原样保留（见
[configuration.md](configuration.md)）。

## 绑定与代次

- 绑定持 `SYNCHRONIZE` 句柄等待退出，等待线程只负责在退出时投递一条带**绑定代次**的消息。
- 主进程只认当前代次：旧绑定的退出回调不会关闭已经切到新生产者的实例。
- 数据源也有代次：换源时递增，旧源迟到的 HTTP 结果按代次丢弃，不会覆盖新源。
- 绑定到同一个 PID 的“进程已退出”竞态：准备阶段会再确认一次；若进程恰好在提交后立刻退出，
  按“生产者已退出”正常收尾，而不是假装绑定成功。

## 返回值与不确定性

| 退出码 | 含义 |
| ---: | --- |
| 0 | 命令已被接受，或条件退出无需操作（`--quit-if-bound` 不匹配、没有实例等），或带 `--wait-exit-ms` 时**已确认实例进程真的退出**。 |
| 2 | 用法错误（未知参数、`--pid` 缺 `--url`、空地址、非法实例名、`--wait-exit-ms` 越界或与别的命令同用等）。 |
| 3 | PID 不合法（保留给更细的 PID 分类；当前实现把 PID 问题统一归到 6）。 |
| 4 | 配置保存失败。 |
| 5 | IPC 超时、没有实例（`--inspect`），或**拿不到/等不到“实例真的退出”的证据**（`--wait-exit-ms`）。 |
| 6 | 命令被拒绝（地址非法、PID 不存在/已退出、绑定失败、正在收尾的实例拒绝接管等）。 |
| 7 | 内部错误（含互斥体仲裁失败、`--inspect` 结果文件读不到）。 |

- **接受命令不等于取数成功**：确认不等待 GET 完成。
- **IPC 超时说明没有收到确认，不能保证命令没有执行**。不能因此强杀、重开或制造第二个常驻实例。
- `--quit-if-bound` 在没有实例、没有绑定或 PID 不匹配时**成功返回**，且不启动接收窗口或数据进程。

### 条件退出与“等到实例真的退出”

缺省（`wait_exit_ms == 0`）时 `--quit` / `--quit-if-bound` 只等 IPC 确认。**确认不等于实例已经退出**：
接收端应答 `Accepted` 之后还要停取数、释放绑定、关控制窗口、退进程。

`--wait-exit-ms <1..60000>` 走一条刻意 fail closed 的路径，它只对 `--quit` / `--quit-if-bound` 生效
（与别的命令同用是用法错误）：

1. 发送**之前**从控制窗口属主取一个 `SYNCHRONIZE` 句柄，并在真正发送前再核一次“窗口还在、属主还是同一个
   PID、句柄还没触发”——防止 `HWND` 被复用之后把请求发给另一个实例；
2. 找不到控制窗口、属主不合法、`OpenProcess(SYNCHRONIZE)` 失败、或发送前身份发生变化 ⇒ **返回 5 且
   **不**发送 IPC**：没有任何“实例是否真的退出”的证据，绝不退化成“只等确认”；
3. 收到 `Accepted` 之后才等那个**发送前捕获的**句柄：在期限内触发 ⇒ 返回 0；到点仍未触发 ⇒ 返回 5
   （命令已被接受、实例可能稍后退出），**绝不补杀、绝不重开、绝不制造第二个常驻实例**；
4. `NotBound`（条件不匹配）⇒ 返回 0 且不等待；`Rejected` / `BadRequest` ⇒ 返回 6。

没有实例时（互斥体没被占）`--quit` / `--quit-if-bound` 一律返回 0 且什么都不做；持有互斥体但控制窗口
已经不在（实例正在收尾：收尾顺序是先关窗口再退进程）时返回 5。这条等待路径**不套用**“窗口不在就当成
没有实例”的启发式——窗口不在不代表进程已经退出。条件退出的接受端还会按**绑定代次**重新核验：投递之后
若已经有新的生产者接管，那条条件退出被丢弃（不退出）。

`--wait-exit-ms` 是通用的“等目标进程结束”开关，不绑定任何私有调用方；不写它时行为与从前逐字一致。

## `--inspect` 输出

`--inspect` 通过同一条控制通道查询运行中的实例；主进程把结果写成
`%LOCALAPPDATA%\DeskFeed[\test-<scope>]\inspect-<发送方 PID>.json`，客户端读完即删。
主进程不会按客户端给的任意路径写文件。

```json
{"instance":"acc1","masterPid":1234,
 "runtimeUrl":"http://127.0.0.1:8099/snapshot","runtimeUrlRedacted":false,
 "diskUrl":"http://127.0.0.1:8099/snapshot","configured":true,
 "boundPid":null,"sourceGeneration":2,"bindingGeneration":1,
 "schedule":{"pollMs":30000,"retryMs":5000,"timeoutMs":8000},
 "nextFetchInMs":12500,
 "view":{"kind":"content","alarm":false,"failure":"none","reason":"",
         "items":[{"id":"cpu","label":"CPU","value":"54℃","state":"ok","detail":""}]},
 "hasSnapshot":true,"expired":false,"receivedAtMs":1791825410342,"expiresAtMs":1791825470339}
```

- `view.kind`：`waiting` / `content` / `error`。`content` 表示**已经接纳一份快照**；`view.items`
  在 `waiting` / `error` 下恒为空数组，而合法的 `items: []` 仍然是 `content`（清空内容不算失败）。
- `view.alarm`：整个视图处于失效/红色呈现时为 `true`，即 `view.failure != "none"` 或
  `expired == true`；健康时为 `false`。
- `view.failure`：`none` / `no-url` / `transport` / `timeout` / `http-status` / `redirect` /
  `too-large` / `encoding` / `parse` / `validation` / `internal`。它**不是**检查器输出的 `kind`：
  检查器按取数层的原因分类（`invalid-url` / `connect` / `send` / `receive` / `empty` /
  `aborted` …，表见 [http.md](http.md)），两者按下面的规则对应——
  `invalid-url` / `connect` / `send` / `receive` → `transport`；`timeout` → `timeout`；
  `redirect` → `redirect`；`http-status` → `http-status`；`too-large` → `too-large`；
  `empty` → `validation`；`aborted` → `none`（主动取消不算失败）；
  校验类原因 `encoding` / `parse` / `too-large` 原样保留，其余归到 `validation`。
- `boundPid`、`receivedAtMs`、`expiresAtMs` 不适用时为 `null`。
- **地址一律脱敏**：去掉 userinfo、查询串与片段；`runtimeUrlRedacted` 记录是否删过东西。
  实际保存与请求的地址保持原样。
- `--inspect` 的退出码：0 收到应答；2 用法错误；5 IPC 超时/没有实例；6 请求被拒绝；7 内部错误。
  `deskfeed.exe` 本身**不使用**退出码 1；`deskfeed-check.exe` 用 1 表示用法/内部错误。

## 崩溃与收尾

- 生产者进程异常退出且没有走卸载回调时，由 PID 绑定等待兜底：实例正常收尾。
- 用户主动退出 DeskFeed 后，生产端不应反复拉起它；桌面端也不会反向启动生产端。
- 收尾顺序：停取数线程 → 释放绑定 → 关闭控制窗口 → 关日志。任何一步失败都只记日志，不阻塞退出。
