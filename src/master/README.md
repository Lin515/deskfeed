# src/master

| 文件 | 作用 |
| --- | --- |
| `main.cpp` | `wWinMain`：取命令行，交给 `master_main`。 |
| `master.h` / `master.cpp` | 主进程全部逻辑：两阶段启动、实例命名空间与安全描述符、单实例仲裁与命令转发、控制窗口处理器、配置事务（校验 → 准备绑定 → 候选落盘 → 提交运行时）、显示面接线（悬浮窗 + 显示邮箱 + 任务栏编排）、取数作业调度与墙钟截止、到期定时器、消息泵、`--inspect` 的 JSON、收尾顺序。 |
| `taskbar_supervisor.h` / `taskbar_supervisor.cpp` | 任务栏组件的**主进程侧编排**：按有界的命令行契约异步地请 `deskfeed-inject.exe` 装载/卸载/查询负载，按退避重试，非阻塞回收子进程。它不注入、不碰界面、不读显示邮箱——真正的注入与目标进程选择都在注入器里。 |

## 两阶段启动：先仲裁，后显示面

`initialize_control()` 只做**控制平面**：控制窗口与心跳、日志、设置文件。`start_display_face()`
才建显示面：显示邮箱、悬浮窗、任务栏编排。

理由是契约里的“先仲裁后副作用”：首份 `--url` 命令被拒绝（地址非法、PID 非法、落盘失败）时，
这个进程除了一个控制窗口和一行日志之外什么都不该留下。无参数启动同样先读保存状态（地址校验
过，或明确判定为“未配置 URL”），之后才建显示面。`--headless` / `--mock` 不建窗口；没有窗口
就没有模态菜单。

心跳（1 s）是**嵌套模态循环**期间唯一还能推进状态机的入口，所以带界面运行时建不出心跳就
fail closed；无界面运行没有模态循环，按有界降级继续并写进日志。

## 显示面：一份 Frame，两个读端

`publish_display_outputs()` 用 `frame_from_view` 算**一份** `Frame`，悬浮窗与显示邮箱各自按
自己的“已发布代次”决定要不要发，所以两面不可能各解释一遍、各显示一个状态。邮箱发布失败不
推进代次（下一轮重发）。托盘屏幕配置（`[taskbar] screens`）也放进这份帧：它不属于 health 的
revision，所以单独比较“已发布的配置”是否变化；变化时即使模型没变也重发一帧。

屏幕配置有两个写入口，都走同一套候选克隆 + 原子替换：悬浮窗菜单的「托盘屏幕」子菜单，以及
负载托盘菜单经控制通道发来的 `ControlOp::SetScreens`（完整启用集合）。两边写入后都由下一次
`pump` 看见配置差异并重发显示帧；退化只是负载的本次落点，从不写回。

任务栏组件分成三件事，缺一个就会写错：

- `component_actual_`：用户的**持久意图**（`[taskbar] component`，缺省 true）；
- `component_capability_`：本次运行**有没有能力**（没关任务栏、邮箱建起来了、注入器真的在）。
  它决定菜单项灰不灰（`WidgetOptions.taskbar_available`）——用 effective 去填会让用户一关组件
  就永久置灰，再也打不开；
- `component_effective_ = actual && capability`：现在到底是不是开着（菜单的勾、编排层目标）。

**没有显示邮箱就连编排层都不武装**：邮箱建不起来时如果只把能力置 false，编排层仍会每轮 tick
去 `--load`，装进去的负载没有帧可读、只会一直失败重试。未武装的编排层是结构上不存在的路径，
比“武装成关”可靠。

## 悬浮窗回调（`widget/window.h` 的契约）

这些回调都在主进程这条线程上被**同步**调用：`refresh` / `quit` 只投一条消息（绝不在回调里
销毁窗口或取数）；`set_taskbar_component` 先候选克隆落盘、成功才改状态并驱动编排层，返回
**实际**状态；`save_preferences` 同样在候选克隆上写 `[window]`，成功才 `adopt`。`SettingsFile`
一直活到窗口 `destroy()` 返回之后（收尾时它还会同步再调一次）。

收尾顺序：请求撤下任务栏负载 → 发布 `closed` 帧 → 关悬浮窗 → 清绑定 → 关控制窗口。

## 消息泵只有一个

主进程的状态推进（到期 tick、整次取数的墙钟截止、取数结果出队、绑定退出、发布显示帧）全部
在 `Master::pump()` 这一份实现里。它有两个入口，但只有一份逻辑：

- 主循环每轮调一次，之后才进入阻塞等待；
- 控制窗口过程收到 `WM_APP` 或心跳 `WM_TIMER` 时调一次。

第二个入口是必需的：右键菜单的 `TrackPopupMenu` 会在主进程线程上开一个**嵌套模态循环**，
主循环那一次 `PeekMessage` 在这期间根本跑不到。所以取数结果走**有界队列 + 一条不带指针的
唤醒消息**（带指针的消息落到 `DefWindowProc` 上会被静默丢掉，结果丢失还漏内存），而心跳
定时器保证模态期间到期与失败仍会被及时发布。

## 任务栏组件的状态模型

`taskbar_supervisor` 里刻意把三件事分开，它们是这份编排最容易写错的地方：

- `enabled_`：**当前目标状态**，只有开关动作改它（`start()` 就把它设成调用方给的初始状态：
  组件本来就关着时，启动不该去 spawn 一次 `--stop`）；
- 待发令牌：还没发出去的装载/停止。关掉组件时落的停止令牌**不会**因为“此刻正好有一个动作
  在跑”而丢，那个动作一结束就优先发它；
- 收尾闩：置上之后不再开新的状态问询或装载，但**仍然**会把还没发出去的停止发掉（用户那次
  关闭用的是一次性停止，不算收尾也停过了）。

任何一次动作的完成都按**此刻的目标状态**重新决策，而不是按发起那一刻的旧意图：关闭组件时
正在跑的那次装载成功回来，也不会把组件重新打开；停止期间用户又把组件打开，停止完成后会重新
问一次状态再决定要不要装回去。

## 时钟域

健康/到期用墙钟 Unix 毫秒，调度与超时用单调时钟。

## 生命周期

单实例仲裁在 `master_main` 里先于控制窗口与日志完成；日志在接收端就绪之后才截断。

取数结果队列用 `shared_ptr` 共享所有权：主进程持一份，每个工作线程也持一份。主进程收尾时
只停止接受新结果并丢掉自己那一份——只要还有线程没真正结束，队列与它的锁就仍然有效。收尾那
几秒的等待是兜底，不是生命周期保证。队列构造**先 reserve 再建锁**：构造函数抛出时析构不会
被调用，先建锁就会漏掉那把已初始化的 `CRITICAL_SECTION`。

工作线程的 C++ 边界只有一处、且在**最外层**：`make_unique<FetchOutcome>`、诊断 catch 里的
`std::string` 拼接与 `what()`、`queue->push`、入队失败时的日志都在内层，任何一种抛出都不会
再跨出线程边界。最外层 catch 只做两件不分配、不记日志的事：置“结果没能入队”标志、投递一条
不带指针的唤醒消息。
